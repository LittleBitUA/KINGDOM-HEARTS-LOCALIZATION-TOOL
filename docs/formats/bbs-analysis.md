# Birth by Sleep — розбір форматів (PC, KH HD 1.5+2.5 ReMIX)

Аналіз зроблено по **реальних файлах гри**, а не лише по документації.
Усе, що нижче помічено як «перевірено», підтверджено робочим парсером.

Джерела: `openkh.dev/bbs/*` (усі 20 сторінок), код `github.com/OpenKH/OpenKh`
(`OpenKh.Bbs`), і власне файли з
`D:\SteamLibrary\...\KINGDOM HEARTS -HD 1.5+2.5 ReMIX-\Image\dt`.

---

## 0. Головне за 30 секунд

| | DDD (те, що вже зробили) | BBS |
|---|---|---|
| текст | `@CTD` версія `0x1F7`, UTF-16LE | `@CTD` **версія 1**, Shift-JIS-подібне однобайтове/двобайтове |
| шрифт | `.bcfnt` (Nintendo 3DS) | `.arc` → `INF`/`MTX`/`CLU`/`COD` (PSP) |
| HD-текстура | PNG ×2 поряд із `.bcfnt` | PNG ×2 поряд із `.arc`, **дві палітри = ліва й права половина** |
| як додати кирилицю | вільні комірки + новий `CMAP` | вільні комірки + нові записи `COD` |
| під які коди | U+0400… напряму | **Shift-JIS сторінка `0x84`** (там і є кирилиця) |

**Найважливіше відкриття:** сторінка Shift-JIS `0x84` — та, де в справжньому
Shift-JIS лежить кирилиця (`0x8440`–`0x8460` = А-Я, `0x8470`–`0x8491` = а-я) —
**повністю вільна в усіх шрифтах BBS**. Тобто українську можна вписати
«за адресою», нічого не ламаючи й не перевизначаючи.

**Друге важливе:** у `mesfont` (діалоги) вільних слотів **270**, і всі вони
всередині наявної HD-текстури. Для 66 українських літер міняти розмір
текстури не доведеться взагалі.

## 1. Структура гри на диску

```
Image\dt\
  bbs_first.hed  + .pkg  + bbs_first.hed_out\    ← система, меню, шрифти
  bbs_second.hed + ...                            ← лише ForEventJP
  bbs_third.hed  + ...                            ← arc_*, chara, Item
  bbs_fourth.hed + ...                            ← основна маса тексту
```

Кожен `*_out` має ту саму пару, що й у DDD:

```
original\    ← дані (метрики, текст, PSP-текстури)
remastered\  ← HD-текстури PNG/DDS, які підміняють оригінальні
```

**Тексту немає** у `bbs_second`. `bbs_third` містить лише `arc_*`/`chara`/`Item`.

### Де лежить англійський текст

| архів | тека | файлів | повідомлень |
|---|---|---|---|
| `bbs_first` | `original\message\en\` | 30 | **1362** (перевірено) |
| `bbs_fourth` | `original\message\en\` | ~103 | ще не пораховано |

Розділи: `system`, `menu`, `map`, `event\<світ>`, `npc_talk\<світ>`,
`mission`, `report`, `shop`, `network`, `battledice`, `minigame`,
`playerselect`. Іменування: `CT<світ><nnn>.ctd`.

Мови поруч: `de`, `en`, `es`, `fr`, `it` (у BBS **немає** `jp` у цих архівах).

> ⚠️ **Технічна перешкода.** Файли на кшталт
> `bbs_fourth.hed_out\original\message\en\event\dp\CTdp400.ctd` лежать на 8
> рівнів нижче підключеної теки, а міст витягує максимум 7. Щоб я дістався
> до всіх, треба **підключити в застосунку теку**
> `...\bbs_fourth.hed_out\original\message` окремо.

## 2. `@CTD` — формат тексту (перевірено)

Це **не той самий CTD, що в DDD**. Спільна лише сигнатура.

```
заголовок 0x20:
  0x00  char[4]  "@CTD"
  0x04  u32      версія = 1                (у DDD було 0x1F7)
  0x08  u32      fileId — старші біти ID усіх повідомлень файлу
  0x0C  u16      layoutCount
  0x0E  u16      messageCount
  0x10  u32      messageOffset  (завжди 0x20)
  0x14  u32      layoutOffset
  0x18  u32      textOffset
  0x1C  u32      reserved (0)

повідомлення 0x0C:
  0x00  u32  унікальний ID  (= fileId | локальний)
  0x04  u32  АБСОЛЮТНИЙ офсет тексту у файлі
  0x08  u16  індекс layout
  0x0A  u16  waitFrames

layout 0x20:  позиція вікна, розмір, вирівнювання, кегль, колір, «хвостик»
              — для перекладу не чіпається

текст:        байтові рядки, кожен завершується 0x00, упаковані впритул,
              БЕЗ дедуплікації
```

Порядок запису: заголовок → таблиця повідомлень → **вирівняти до 16** →
таблиця layout → текст → хвіст `0xCD` до межі 16 байтів.

**Перевірка:** усі 5 витягнутих файлів (`CT00000`, `CT00100`, `CTit000`,
`CTmn100`, `CTdp000` — 1362 повідомлення) розбираються й збираються
**побайтово ідентично**.

### ⚠️ Документація openkh.dev тут ПОМИЛКОВА

`openkh.dev/bbs/file/type/ctd.html` каже, що повідомлення має розмір
**0x10** (`0x08 int32 Layout index`, `0x0C int32 Wait Frame Count`).
Насправді крок **0x0C**, обидва поля — `u16`. Арифметика на реальному файлі:
`0x20 + 202*0x0C = 0x9A0` — рівно той `layoutOffset`, що в заголовку.
З кроком `0x10` не сходиться в жодному файлі.

Також документація називає `0x08` «RESERVED + Unknown», хоча це `fileId`.

Код OpenKh (`OpenKh.Bbs/Ctd.cs`) — правильний; документація на сайті — ні.

## 3. Кодування тексту (перевірено)

Однобайтове ASCII + двобайтові Shift-JIS-сторінки:

| байт | що це |
|---|---|
| `0x0A` | перенос рядка |
| `0x20`–`0x7E` | ASCII (але `0x5C` = `¥`, не `\`) |
| `0x81 xx` | пунктуація/символи (Shift-JIS рядок 1) |
| `0x99 xx` | **латинські діакритики**: `À Á Â Ä Æ Ç … © ® ™` |
| `0x82`, `0x83`, `0x87`, `0x8A`, `0x8F`, `0x95`, `0x96` | інші SJIS-сторінки (вживаються рідко) |
| `0xF1 xx` | іконки кнопок (△ ○ □ × L R аналог хрестовина) |
| `0xF2 xx`, `0xF5 xx` | ще іконки |
| `0xF9 xx` | колір тексту (`41` типовий, `58` білий, `59` жовтий) |

Приклад із гри: `4D 65 6D 6F 72 79 … 99 CD 20 61 63 63 65 73 73` →
`Memory Stick Duo™ access` (`99 CD` = `™`, індекс 0x4D у таблиці `0x99`).

Статистика по 1362 повідомленнях `bbs_first`: `0xF9` — 131 раз,
`0xF5` — 91, `0xF1` — 23, `0x81` — 7, решта одиничні.

### Помилки в OpenKh, які не варто повторювати

Аналіз коду виявив кілька багів у їхньому кодувальнику:

1. **Таблиця `0x81` при кодуванні зсунута на 0x50.** Декодер читає
   `param - 0x40`, а зворотна таблиця будується від `0x8190 + i`. Має бути
   `0x8140 + i`. **60 символів кодуються не в ті байти.**
2. `FromUcs` видає і однобайтовий, і двобайтовий варіант для кожного символа
   (немає `continue`) — `0x8190` перетворюється на `24 81 90` = `"$$"`.
3. Для нерозпізнаних SJIS-старших байтів (`0x82`–`0x98`, `0xE0`–`0xEF`)
   зʼїдається **один** байт замість двох — далі весь рядок «пливе».
4. `_mapping81[param-0x40]` падає при `param < 0x40`; `_mapping99` — поза
   межами при `param > 0xCF`.
5. Три різні керуючі байти (`0xF1`, `0xF2`, `0xF5`) мають однакове імʼя
   команди `icon` → `{:icon unk}` неможливо закодувати назад.

Мій парсер це вже обходить: кожен старший байт зʼїдає рівно 2 байти,
у команд різні імена, межі перевіряються.

## 4. Шрифти

### 4.1 Контейнер `.arc` (перевірено)

`original\arc_en\system\FontEn.arc` — 218 416 байтів, **ARC версії 1, 23 записи**.

```
заголовок 0x10:  "ARC\0", u16 версія=1, u16 кількість, 2×RESERVED
запис 0x20:      u32 dirHash, i32 offset, i32 length, u32 RESERVED,
                 char[16] імʼя (UTF-8, доповнене нулями)
```
`dirHash != 0` = це посилання на файл в іншій теці, `length` = 0.
У `FontEn.arc` посилань немає — усі 23 записи власні.

Шість шрифтів × чотири файли (у `FontIcon` немає `.cod`):

| шрифт | де видно | комірка | текстура | символів | MTX |
|---|---|---|---|---|---|
| `mesfont` | діалоги | 28×28 | 512×512 | 378 | 79 872 |
| `helpfont` | підказки | 20×20 | 512×256 | 378 | 41 100 |
| `menufont` | меню | 20×20 | 512×256 | 336 | 36 864 |
| `cmdfont` | команди в бою | 16×16 | 512×128 | 378 | 24 808 |
| `numeral` | цифри | 10×10 | 512×16 | 24 | 4 096 |
| `FontIcon` | кнопки, іконки | — | 256×64 8bpp | 21 | 16 388 |

### 4.2 `INF` / `COD` / `CLU` / `MTX`

```
INF  8 байтів:  u16 кількість, u16 ширина текстури, u16 висота,
                u8 ширина комірки, u8 висота комірки

COD  8 байтів на символ (лічильника немає — count = розмір/8):
                u16 Character ID  (це код Shift-JIS!)
                u16 X, u16 Y      (позиція в текстурі, вирівняна по сітці)
                u8  палітра (0 або 1)
                u8  реальна ширина літери  ← це і є advance

CLU  256 байтів = 4 палітри × 16 кольорів × RGBA
     (документація каже 1024 — це неправда для 4-бітних шрифтів;
      1024 має тільки FontIcon, бо він 8-бітний)

MTX  4-бітна індексована текстура, засвізлена блоками 16 байтів × 8 рядків,
     після розсвізлення треба поміняти місцями напівбайти.
     Файл КОРОТШИЙ за width*height/2 — порожні блоки в кінці не зберігаються.
```

Мій декодер `MTX` + `CLU` відтворює оригінальні гліфи один-в-один.

### 4.3 Трюк із двома палітрами (перевірено)

Одна й та сама 4-бітна картинка під палітрою 0 і під палітрою 1 показує
**різні набори символів**. Тобто в комірці на позиції (X,Y) насправді
сидять ДВА гліфи, і `COD.палітра` каже, який саме.

Палітра 0: `X C E G I K M O Q S U W Y À Â Æ È Ê …`
Палітра 1: `B D F H J L N P R T V X Z Á Ä Ç É Ë …`

### 4.4 HD-текстури (перевірено — головне)

`remastered\arc_en\system\FontEn.arc\US_FontEn_arc0..5.png`

HD-версія не вміє палітр, тому **розклала обидві палітри поряд**:
ліва половина PNG = палітра 0, права = палітра 1.

```
png_x = COD.X * 2 + палітра * (ширина_PNG / 2)
png_y = COD.Y * 2
розмір гліфа = комірка * 2
```

Перевірено попіксельно: гліфи `A B C a b !`, вирізані з PNG за цією
формулою, збігаються з гліфами, розкодованими з `MTX`+`CLU`.

| PNG | шрифт | розмір | покриває рядків |
|---|---|---|---|
| `arc0` | menufont | 2048×288 | 144 з 256 |
| `arc1` | helpfont | 2048×320 | 160 з 256 |
| `arc2` | cmdfont | 2048×192 | 96 з 128 |
| `arc3` | FontIcon | 1024×512 | (перероблена для PC) |
| `arc4` | **mesfont** | 2048×1024 | **512 з 512 — уся** |
| `arc5` | numeral | 2048×32 | 16 з 16 |

### 4.5 Скільки місця вільно

| шрифт | сітка | вільних слотів у заявленій текстурі | з них уже в межах PNG |
|---|---|---|---|
| `mesfont` | 18×18 | 270 | **270** ✅ |
| `menufont` | 25×12 | 264 | 14 |
| `helpfont` | 25×12 | 222 | 22 |
| `cmdfont` | 32×8 | 134 | 6 |
| `numeral` | 51×1 | 78 | 78 |

Для української треба **66** гліфів.

* **`mesfont` (діалоги) — можна робити хоч зараз**, нічого не збільшуючи.
* Для решти PNG доведеться дорастити донизу до заявленої в `INF` висоти
  (наприклад `helpfont`: 2048×320 → 2048×512). Це майже напевно спрацює,
  бо рушій і так виділяє буфер за розміром з `INF`, а `MTX` подає коротший
  — але це треба **перевірити в грі**, це єдине справді невідоме місце.

### 4.6 Чому сторінка `0x84` — правильна відповідь

Зайняті сторінки `Character ID` по всіх шрифтах:

```
0x81 — 56 ID    0x82 — 142    0x83 — 86    0x87 — 10
0x8A — 1        0x8F — 1      0x95 — 1     0x96 — 1     0x99 — 80
0x84, 0x85, 0x86, 0x88 — ПОРОЖНІ
```

У справжньому Shift-JIS сторінка `0x84` — це саме кирилиця. Отже:

1. у `COD` додаємо записи з `Id = 0x8440…0x8491`;
2. у тексті `.ctd` пишемо ті самі два байти;
3. рушій (`0x80`–`0x9F` → зʼїдає другий байт → шукає в `COD`) знайде їх сам.

Нічого перевизначати, нічого ламати. Латиниця, діакритики, іконки лишаються.

## 5. Що ще не перевірено

1. **Чи стерпить рушій вищий PNG** (для `helpfont`/`menufont`/`cmdfont`).
   Перевіряється одним експериментом: дорастити прозорими рядками й запустити.
2. **Чи читає PC-версія `original\*.mtx`взагалі**, чи тільки `remastered` PNG.
   У DDD патчили обидва — тут варто так само, про запас.
3. **Звідки беруться зайві іконки клавіатури** (`F1`–`F12`, Shift, Ctrl…)
   у `arc3` — у `FontIcon.inf` лише 21 запис.
4. **Чи є текст у `.exa`** (сцени). У DDD не було — там лише скрипти.
   У BBS `.exa` теж імовірно без тексту, але треба глянути.
5. **Точна кількість повідомлень у `bbs_fourth`** — упирається в обмеження
   глибини шляху (див. п.1).

## 6. План робіт

1. Підключити теку `...\bbs_fourth.hed_out\original\message` у застосунку.
2. Дописати `bbsctd.py` до повного інструменту (експорт/імпорт `text_all.txt`
   такий самий, як для DDD — формат `### шлях` / `#N` / текст).
3. Експеримент із висотою PNG на `helpfont`.
4. Кирилиця в `mesfont` (найпростіше, місця вистачає) → тест у грі.
5. Далі `helpfont`, `menufont`, `cmdfont` — коли підтвердиться п.3.
6. `numeral` і `FontIcon` кирилиці не потребують.
