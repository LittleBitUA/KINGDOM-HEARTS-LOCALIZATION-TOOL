# Окремий встановлювач українізатора

Те, що отримує гравець: одна консольна програма, яка сама знаходить теку гри,
сама робить резервну копію і сама застосовує `.pcpatch`. Ані .NET, ані mono,
ані KHPCPatchManager поруч не потрібні — усе всередині одного файла.

Працює під **Windows** і під **Linux / Steam Deck**.

```
node tools/patcher/build.js                              # обидві платформи
node tools/patcher/build.js --rid win-x64                # лише Windows
node tools/patcher/build.js --patches "C:\…\PATCH\KH1-UA" # вкласти патчі в реліз
node tools/patcher/build.js --clean                      # перезавантажити вихідники
```

Результат — `tools/patcher/dist/`:

| файл | для кого |
|---|---|
| `KH-UA-Patcher-win-x64.zip` | Windows: розпакувати, запустити `INSTALL.bat` |
| `KH-UA-Patcher-linux-x64.tar.gz` | Linux / Steam Deck: розпакувати, `./install.sh` |

Для збірки потрібен **.NET SDK 8** (`dotnet --info`). На машині гравця — нічого.

## Чому не xdelta і не готовий KHPCPatchManager

`.pcpatch` — це не двійкова різниця, а zip із заміненими файлами гри; накотити
його означає перезібрати `.pkg` разом із `.hed`. Це вміє лише KHPCPatchManager
(і OpenKH, на якому він стоїть), тож ми беремо саме його код.

Але його реліз під Linux не працює. У `.csproj` написано `net5.0`, однак збирають
його власною ціллю `<Csc>`, тобто під .NET Framework — звідси і 1,5 МБ замість
~30, і потреба у Windows. Тому ми збираємо його заново з вихідників.

## Що саме ми змінюємо у KHPCPatchManager

Вихідники тягнемо з GitHub на закріпленому теґу (`TAG` у `build.js`), кладемо в
`.vendor/` і латаємо на льоту. Кожна правка перевіряє, що знайшла рівно стільки
збігів, скільки очікує — якщо апстрім змінився, збірка падає, а не збирає мовчки
щось інше. Перелік правок лягає у `NOTICE.txt` поруч із програмою (Apache-2.0).

- **GUI на `System.Windows.Forms` прибрано.** Він є лише під Windows, а нам
  потрібна консоль. Разом із ним ідуть `DllImport` у `user32`/`kernel32`.
- **`ZipManager` переписано.** Порівняння шляхів усередині `.pcpatch` ішло через
  селектори DotNetZip із `\`; під Linux патч через це «не бачив» власних тек.
- **Шлях до `remastered`** будували заміною `"\original\"` на `"\remastered\"` —
  під Linux роздільник інший, і HD-текстури з патчу просто ігнорувались.
- **`Helpers.GetAllFiles` / `GetRelativePath`** відрізали префікс через `"\"`;
  зведено до спільного `Rel()`, який нормалізує **обидва** боки до `/`.

Остання правка навмисне зроблена не через `Path.DirectorySeparatorChar`:
після неї в пропатчених вихідниках **не лишається жодної гілки, залежної від
роздільника ОС** (перевіряється `grep`-ом по `.build/upstream`). Отже під
Windows і під Linux виконується той самий код — і перевірка Windows-збірки
щось та й означає для Linux-збірки.
- **`Main` → `CliMain`.** Точку входу дає наш встановлювач; повний режим самого
  KHPCPatchManager лишається доступним через `--cli`.

Ще одне, вже не в їхньому коді: DotNetZip читає імена записів кодуванням IBM437,
якого в .NET немає без `CodePagesEncodingProvider`. Без нього **жоден** `.pcpatch`
не відкривається. Апстріму це не заважає лише тому, що він під .NET Framework.

## Чим наше застосування патчу відрізняється

В апстрімі живий `.pkg` **переносять** у `backup/`, затираючи те, що там лежало.
Пропатчив двічі — і в резервній копії вже не оригінал, а результат першого
патчу: відкотитись нічим, а патчі різних версій нашаровуються.

У нас навпаки: **якщо резервна копія вже є, вона недоторканна й служить
джерелом**. Тому повторне застосування завжди рахується від чистої гри й дає
той самий байт-у-байт результат. Звідси ж безкоштовно береться `--відкотити`.

## Як гравець це бачить

```
УКРАЇНІЗАТОР KINGDOM HEARTS   1.0   (Windows)
────────────────────────────────────────────────────────────
KINGDOM HEARTS Birth by Sleep FINAL MIX
  патч: BBS-UA.bbspcpatch  (3 МБ)
  гра:  …\KINGDOM HEARTS -HD 1.5+2.5 ReMIX-\Image\dt   [Steam]
  bbs_first: відкладаємо оригінал у backup/
  bbs_first: 100%
  ✓ Готово за 5 с. Перезібрано архівів: 1 (bbs_first).
```

Ключі: `--гра <тека>`, `--відкотити`, `--без-копії`, `--так`, `--список`,
`--cli …`. Те саме, що `--гра`, робить змінна оточення `KH_GAME_DIR`.
Докладний журнал лягає у `patch-log.txt` поруч із програмою.

## Де шукається гра

Steam: реєстр (Windows) → `libraryfolders.vdf` → усі бібліотеки на всіх дисках;
під Linux ще `~/.steam`, `~/.local/share/Steam`, flatpak-тека і `/run/media`
(SD-картка Steam Deck). Далі `appmanifest_2552430.acf` / `2552440.acf` дає теку
збірки. Epic — через маніфести лаунчера. Не знайшлось — програма попросить шлях.

## Чим перевірено

Головне: на одній і тій самій копії `bbs_first.pkg` (324 МБ, 33 записи в
`remastered` — саме той шлях, що ламався під Linux) **наша збірка й офіційний
KHPCPatchManager дали однаковий MD5** `c35341a3111f1618a79a4c32479644c4`.
Тобто перезбирання архівів не змінилось ні на байт.

Крім того: автопошук знайшов гру в бібліотеці Steam на `E:`; повторне
застосування дало той самий MD5 (резервну копію не зачеплено); `--відкотити`
повернув оригінал.

**Не перевірено:** двійковий файл для Linux зібрано, але не запущено — на цій
машині немає ані Linux, ані WSL, ані контейнерів. Ризик знижено тим, що
платформо-залежних гілок у пропатченому коді не лишилось (див. вище), а наш
власний Linux-код — це лише перебір тек у `GameFinder`, який у найгіршому разі
просто попросить шлях руками.

Як перезвірити після оновлення `TAG`:

```bash
node tools/patcher/build.js --clean --rid win-x64
grep -rn 'DirectorySeparatorChar\|\\\\original\\\\' tools/patcher/.build/upstream   # має бути порожньо
```
